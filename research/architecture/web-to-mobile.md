# From a browser WMS to a floor app

For a 2027 retail rollout, prototype the same receiving task in a browser first. If a managed handheld needs native scanner events, a Capacitor shell can carry forward the web screens. If floor work calls for a distinct interface across many tasks, compare a React Native/Expo floor client sharing the same commands with the desktop app. The deciding evidence is whether staff can receive the right item, at working speed, through a connectivity loss and shift handoff.

This shortlist assumes a browser-based supervisor desk and an as-yet-unconfirmed mix of floor devices. Sources were checked on 26 November 2026. Browser capabilities, supported OS versions, plugin maintenance and device-management policies for the 2027 fleet remain uncertain.

## Three paths

| Path | What carries forward | What could change the choice |
| --- | --- | --- |
| Responsive web app, optionally installed as a progressive web app (PWA) | One DOM interface for a browser tab and an installed app. A service worker can cache the app for offline launch after provisioning. | Try this where the scanner sends keystrokes and reopening the app for sync is acceptable. Storage can be evicted and Background Sync coverage varies. Test both the tab and installed mode under fleet policies. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/) · [Chrome Background Sync](https://developer.chrome.com/blog/background-sync) |
| Capacitor with a bundled web app | Existing web screens, routing, validation and client state run inside a native shell. Platform plugins provide a bridge to device APIs. | A targeted Android scanner receiver or native database can justify a shell. Each native dependency adds a build, signing, upgrade and fleet-distribution obligation. A WebView still needs a focus and keyboard trial. [Capacitor runtime](https://capacitorjs.com/docs) · [Capacitor build workflow](https://capacitorjs.com/docs/basics/workflow) |
| React Native/Expo with web | TypeScript domain code and components designed around React Native primitives can run across platforms through React Native for Web. Desktop tables can use web-specific components. | Prototype this when floor navigation, hardware and screens diverge from the desk. Ordinary DOM tables and CSS need a native implementation or an intentionally embedded web view. Verify camera support and any OEM scanner module on a native build. [Expo web development](https://docs.expo.dev/workflow/web/) · [Expo Camera](https://docs.expo.dev/versions/latest/sdk/camera/) |

## Technology shortlist

- **Web framework.** React Router framework mode with a client-rendered React app produces deployable static assets for a browser and a future shell. Expo Router with React Native for Web is a second candidate if touch-oriented floor screens dominate the shared product. Compare them with one dense receipt grid on a keyboard and one one-handed receiving flow. [React Router single-page apps](https://reactrouter.com/how-to/spa) · [Expo web development](https://docs.expo.dev/workflow/web/)
- **Local data.** Use an IndexedDB transaction to save an observation, its stable command ID and its pending state together. On a packaged client, compare an app-owned SQLite database behind the same operations. Expo supplies one native binding. Validate migrations with unsent work present. WebKit documents quota failures and eviction, so display “saved on device” only after the write succeeds and retry transmission on foreground resume. Keep user and site ownership attached through logout and handoff. [W3C IndexedDB](https://www.w3.org/TR/IndexedDB/) · [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/) · [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/)
- **Scan capture.** Start with a keyboard-wedge adapter for integrated or paired scanners and a manual-entry path. Zebra’s DataWedge can send characters and Enter or Tab. Check where focus moves and whether separators survive. Its Android Intent output offers structured scan data to an associated native app. A Capacitor plugin or Expo native module can expose those events. On phones, evaluate camera decoding separately with the actual labels and lighting. [Zebra keystroke output](https://techdocs.zebra.com/datawedge/latest/guide/output/keystroke/) · [Zebra Intent output](https://techdocs.zebra.com/datawedge/latest/guide/output/intent/) · [Expo Camera](https://docs.expo.dev/versions/latest/sdk/camera/)
- **API contract.** Describe the HTTP operations and payloads with OpenAPI. Share the generated types, scan parsing, quantity conversions, validation and queue state transitions as plain TypeScript. Keep navigation, local database access, credentials and scan callbacks in each client. Specify replay and conflict behavior with examples so an older handheld can submit a pending receipt after a server upgrade. [OpenAPI specification](https://spec.openapis.org/oas/v3.1.1.html) · [Inventory command and retry example](replaceable-modules.md)

## Release and reversal

For a look-up screen, switching clients can be as simple as opening a URL. A receiving station has pending writes. Before moving a device from PWA to shell, synchronize its queue and compare the acknowledged command IDs at the server. A device with an unresolved command needs access to the old client until the outcome is known. A new app installation has its own storage context. Rehearse this same transition in reverse on one device.

During a staged rollout, accept the supported earlier command format, retain its unit semantics and test a duplicate sent by the old client after the new client has displayed the receipt. Version local storage migrations and defer retiring an old format until queued operations can be read or safely replayed. For Expo updates, native-module changes require a compatible native build and matching runtime version. For Capacitor, synchronize the web assets and plugins into the native project and test the signed package deployed by fleet management. [Expo runtime versions](https://docs.expo.dev/eas-update/runtime-versions/) · [Capacitor build workflow](https://capacitorjs.com/docs/basics/workflow)

## Floor-device trial

1. Record the actual handheld model, imager, OS, browser/WebView, scanner profile, management policy and label formats. Include the oldest supported device and a representative desk browser. Confirm whether shared iPhones or iPads are in scope before budgeting for an iOS build.
2. Have a receiver scan a location, retail item and case label through a normal carton, then enter a damaged label manually. Include deliberate repeated scans of identical items. Measure wrong-field captures, dropped or duplicated reads, and median and 95th-percentile time from trigger to visible confirmation. Compare with the team’s current receiving pace.
3. Disconnect after a scan and again after server commit but before the reply. Lock and restart the device, switch operators and then reconnect. Pass when every locally acknowledged scan is accounted for, stock is posted once per intended operation, and pending work retains its operator and site. Exercise a failed local write and verify that the worker sees recovery instructions.
4. Deploy an update with a pending receipt, roll back on one station, and reconcile against the receipt line and stock movements. Keep the browser if it meets the agreed pace, recovery and deployment needs. Trial Capacitor for an identified hardware gap. Advance Expo if its floor UI or device support produces a measurable gain worth the additional implementation.
