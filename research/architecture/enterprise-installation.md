# What a customer-operated WMS installation would include

An enterprise customer should be able to bring a domain, a supported computing environment, storage and an identity provider, then receive and dispatch goods using the same WMS release as a pooled merchant. The customer controls its DNS, operational data, keys, backup destinations, outbound connections and update window. A vendor-operated dedicated deployment can use the same package with a different operator. This is a proposed product and acceptance contract. Its viability depends on a restore and upgrade rehearsal on infrastructure representative of the first buyer. [Tenant layouts and merchant migration](tenant-isolation.md)

## Deliver one release with a documented operating contract

| Release component | What the customer should receive |
| --- | --- |
| Application and workers | Versioned OCI images by digest for the supported OS and CPU architectures, including built frontend assets, fonts, scanner libraries and migrations. List the API, worker and one-shot maintenance entry points. Provide a registry mirror or an offline archive, a release manifest binding all digests together, signatures, verification material and a software bill of materials. Verify publisher identity through a separately trusted key or approved signing identity. A digest identifies content. [OCI image format](https://github.com/opencontainers/image-spec) · [OCI descriptors](https://github.com/opencontainers/image-spec/blob/main/descriptor.md) · [Sigstore verification](https://docs.sigstore.dev/cosign/verifying/verify/) |
| Configuration | Versioned configuration schema with typed defaults and startup validation. Include canonical external URL, trusted ingress, tenant mode, database access, storage endpoint, identity settings, certificate trust, locale, time zone and feature flags. Document which changes need restart. Accept customer-injected credentials or mounted secret references and support rotation. Keep exported configuration free of secret values. |
| Required and optional dependencies | Publish supported PostgreSQL versions and extensions, file-storage API and durability semantics, job persistence and concurrency behavior. A candidate baseline uses a database-backed queue and a customer-supplied file store. Identify anything else a chosen implementation requires. Document optional email, external identity, metrics, search and carrier or sales connectors with endpoints, data fields and effects of outage. Keep every vendor-specific adapter behind a documented interface. |
| Data portability | Include versioned logical exports and import procedures covering catalog revisions, historical units, movements, lots, holds, permissions, open work, attachments, audit history and idempotency records. Supply stable IDs, field definitions, checksums, an archive of the schema and explicit handling for secrets that need reauthorization. Test reimport into a clean installation. A CSV of current balances alone cannot reconstruct a disputed receipt. |
| Administration and diagnosis | Supply local health/readiness checks, worker backlog, migration status, reconciliation tools and local logs with documented redaction. A customer administrator can generate a scoped support bundle, inspect it and decide whether to send it. Support access uses named, expiring grants and a local audit trail. [Tenant support-access model](tenant-isolation.md) |

Agree a support matrix for the trial. One documented image runtime and one tested PostgreSQL major might be enough for the first customer. Additional database engines, CPU families and orchestrators create distinct support obligations. An OCI image defines packaging. The customer still needs supported storage, secrets, identity, networking and recovery procedures. [OCI distribution specification](https://github.com/opencontainers/distribution-spec)

## Keep the customer in control of the domain and network

The customer registers and controls its hostname, routing and TLS certificates. Register that exact origin for login callbacks and generate canonical links and webhook targets from approved configuration. Use the customer's identity provider with a documented issuer, audience, key rotation and recovery administrator procedure. Provide an authentication option reachable inside the customer network. Map users to authorized merchant roles and sites after sign-in. A new hostname is a new browser origin, so finish or reconcile queued device observations before changing it. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html) · [Multitenant domain lifecycle](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/domain-names)

For independent operation, design core login, stock reads and postings, history, printing, exports, background work and recovery to use only customer-controlled services. Ship static assets locally. Updates and license renewal, if applicable, should support verified packages transferred by the customer and an explicit offline policy. Telemetry and remote support are opt-in. An installation that loses access to a configured carrier records the booking as pending or uncertain and exposes the manual handoff path. External integrations necessarily depend on the services the customer enables.

**Independence trial.** Starting with the approved release archive, allow connections only to the customer’s internal dependencies. Install, sign in, receive two cases, print a label, reserve one unit, restart the worker, export the ledger and recover from backup. Record all DNS and outbound dependencies encountered by browser, server, worker and maintenance tool. Check the same operations after the documented license or offline-renewal boundary and with telemetry disabled. Define any renewal notice or restricted operation in the commercial agreement before promising availability.

## Upgrades, recovery and tenant moves

1. **Upgrade against existing work.** Publish supported upgrade paths, schema version ranges, disk and time requirements derived from a representative rehearsal, and minimum client compatibility. Run preflight checks, take a recoverable checkpoint and ensure one authorized migrator executes a revision. Use resumable backfills and keep earlier clients able to submit queued operations. Test an interrupted migration and an old six-bag receipt against a new five-bag pack. [Historical-unit migration](code-practices.md)
2. **Define rollback per release.** Record which old app binaries can read the new schema. Switching images is sufficient only when the schema, data and queued jobs remain compatible. Otherwise advance with a tested correction or fence writers, recover the earlier checkpoint and replay all later accepted business commands under their original IDs. Reconcile externally visible handovers and outbound deliveries before restarting publishers.
3. **Back up the whole business record.** Declare a coordinated recovery point for database state, object versions, configuration, queue/outbox checkpoints and required keys. Protect keys separately and confirm that authorized operators can restore them. Decide the maximum acceptable data loss and recovery time with the customer, then measure both. PostgreSQL distinguishes logical dumps, file-level backups and continuous archiving/PITR. These have different recovery scopes and prerequisites. A complete application restore also depends on files and secrets. [PostgreSQL backup and restore](https://www.postgresql.org/docs/18/backup.html) · [GitLab application restore example](https://docs.gitlab.com/administration/backup_restore/restore_gitlab/)
4. **Prove recovery in isolation.** Restore into a clean customer-controlled environment with external publishers held. Compare opening stock plus movements to balances by site, unit and disposition. Verify open reservations, pending transfers, exceptions, audit links, attachment hashes and replayed commands. Inspect carrier and checkout acknowledgments before clearing the outbound hold. Confirm that production endpoints receive zero callbacks from the rehearsal.
5. **Prove scoped export and exit.** For a pooled-to-dedicated move, create A and B with identical external receipt IDs and distinct files. Move only A at a fenced checkpoint. Verify A’s authorized user can retrieve each expected object and that the manifest, restored database, search results, support output and webhook queue contain no B business data. Leave B operational. If the customer exits, supply its documented export, revoke credentials, detach domains and agree retention and eventual expiry of backup copies. [Tenant migration procedure](tenant-isolation.md)

## Who operates what?

| Question | Pooled SMB service | Customer-operated enterprise installation |
| --- | --- | --- |
| Who runs updates and recovery? | Vendor releases and restores the shared service. Merchant verifies balances and scoped exports. | Vendor supplies compatible, verifiable releases and tested recovery procedures. Customer schedules, runs and verifies them. Name who will assist during a failed upgrade. |
| Who controls access and evidence? | Merchant grants its staff roles. Vendor controls infrastructure access under the support-access policy. | Customer controls identity, credentials, backups and support access. Vendor receives only explicitly shared diagnostics or time-limited access. |
| Who owns integrations and continuity? | Merchant authorizes its source connections. Vendor operates delivery, retry and reconciliation within the service. | Customer owns credentials and egress policy and monitors jobs. Vendor documents protocol behavior and helps reconcile failures. Assign owners for the customer’s DNS, TLS renewal and restore rehearsal. |

**Before quoting a 2027 installation**, confirm the buyer’s network policy, required platform and CPU, identity and certificate control, dependency availability, release window, restore targets, support staffing and offline entitlement expectations. Primary documentation was checked on 26 November 2026. Revalidate supported versions, signing procedures and image compatibility against the release actually offered.
