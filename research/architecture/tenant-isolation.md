# One WMS for many merchants

A merchant owns its catalog, orders, staff permissions and stock. A store is a location inside that merchant. Two merchants can both use “Store A”, SKU 0042 and receipt 412. A user can also work for both companies. A useful acceptance test is whether that user can switch merchants midway through a shift without mixing a queued scan, pickup bag, cached balance or export.

For the SMB service, **trial shared application processes and shared PostgreSQL tables with tenant-scoped constraints and row-level security (RLS)**. Keep the tenant ID immutable and give the application a directory mapping it to its current data location. This makes moving an individual merchant possible. Select a separate database or installation when the customer's restore, isolation or control needs warrant its cost. These are proposed choices informed by the documented pool, bridge and silo models. [AWS PostgreSQL tenancy guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/) · [Enterprise installation contract](enterprise-installation.md)

## How a request selects its merchant

For the hosted pilot, offer an account chooser at a shared sign-in address and send each member to a named merchant subdomain. A shop can bookmark that address on its scanners. In a dedicated installation, use the customer's configured hostname as the usual entry point for the same application. Keep the immutable merchant identifier inside the application in both modes. Domain changes, store openings and staff membership changes then have separate lifecycles.

| Entry | Benefit and cost | Required check |
| --- | --- | --- |
| Vendor subdomain, e.g. `acme.wms.example` | Recognizable bookmark and distinct browser origin for each merchant. Requires host and certificate management. A change of origin also affects local scanner queues. | Resolve the registered host to an immutable tenant ID. Use host-only sessions where appropriate. Reauthorize membership and site/action access on each request. |
| Shared origin with a path, e.g. `wms.example/m/acme` | One origin and sign-in entry. Browser storage and service-worker scope can span merchants. Convenient for users with several memberships. | Partition local records and caches by tenant and user. Confirm the active merchant on resuming pending work. Compare route tenant with authorized membership. |
| API credential or authenticated tenant selection | Stable for integrations and devices that do not follow a browser URL. | Bind the credential to the installation, tenant, permitted sites and operations. If a host, path or resource disagrees, reject before returning any resource or cached command result. |

The host or path helps locate a tenant. Authorization comes from a verified identity and its current grant in that tenant. For a user with multiple memberships, explicitly select one. Accept forwarded host information only from the configured ingress and use a registered host when building outward links. A renamed shop retains its tenant ID and history. [Microsoft request-to-tenant mapping](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/map-requests)

**Custom domains have a lifecycle.** Record the requested domain and tenant, verify the merchant controls the name, validate DNS and certificate coverage, then activate it. Maintain renewal ownership, expiration alerts, approved sign-in callback URLs and a tested fallback address. On departure disable routing and sessions, revoke callbacks, retire the certificate binding and coordinate DNS removal. Require fresh domain-control proof before reassignment. Drain pending offline work on the old origin before retiring it. [Microsoft multitenant domain guidance](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/domain-names)

## Storage choices

| Layout | What it provides | What carries operational risk |
| --- | --- | --- |
| Shared tables, tenant column and RLS | One schema migration and efficient sharing for small accounts. A tenant can move later using a bounded export. | Missing policies or overprivileged code can expose many merchants. Queries, indexes, quotas and restore tooling must all handle tenant scope. |
| Schema per tenant in one database | Separate namespaces and per-schema grants. Useful with a limited fleet if schema-level extraction or independent upgrade sequencing matters. | Each schema needs migration tracking. Shared resources and database-level recovery remain. Resolve schemas from a trusted registry, restrict creation privileges and qualify names in privileged code. [PostgreSQL schema and search-path behavior](https://www.postgresql.org/docs/18/ddl-schemas.html) |
| Database per tenant in a shared cluster | Independent database credentials, logical dumps and connection routing. Useful for an independently restorable merchant or a larger account. | Connections, migrations and monitoring multiply. Cluster administration, capacity and physical point-in-time recovery remain shared. A database-specific logical restore has different recovery characteristics. [PostgreSQL backup approaches](https://www.postgresql.org/docs/18/backup.html) |
| Dedicated installation | Separate application, workers, data stores and credentials. Vendor-operated and customer-operated are different responsibility models. | Each installation needs release, recovery and support evidence. Additional isolation depends on whether queues, file stores, keys and administrators are also separate. [Enterprise installation contract](enterprise-installation.md) |

## PostgreSQL boundaries to prove

- Every tenant-owned table carries a non-null tenant ID. A movement referencing a location uses a composite foreign key from `(tenant_id, location_id)` to a unique parent pair. Scope stock keys, aliases and client idempotency keys similarly. Foreign keys check integrity independently of RLS. Map constraint failures to ordinary tenant-safe errors. [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html) · [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)
- A migration role owns protected tables and policies. The runtime role has the necessary data privileges only. Enable RLS for each protected table, define visible rows and permitted inserted/updated rows, and test missing context as a denial. Superusers and roles with `BYPASSRLS` bypass row policies. Table owners normally bypass them too. `FORCE ROW LEVEL SECURITY` subjects owners to policies in ordinary operation, while ownership still grants the ability to change them. Review privileges for views, privileged functions, workers and backup operators separately. [PostgreSQL row-security behavior](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)
- With a pooled application role, start an explicit transaction on one checked-out connection. Set verified tenant context transaction-locally before the first tenant query, use that connection for every statement, then commit or roll back. Apply this to reads, retries and workers. A custom setting is supplied by trusted application code and depends on that code authenticating the caller. Test A, a rolled-back B operation, a missing-context request and A again through a pool of one. Verify membership restrictions separately for two stores within A. [PostgreSQL transaction-local settings](https://www.postgresql.org/docs/18/sql-set.html) · [PgBouncer pooling modes](https://www.pgbouncer.org/features.html)

## Carry the boundary outside the stock ledger

| Surface | Isolation evidence to collect |
| --- | --- |
| Jobs, imports and dead letters | Persist the tenant, original identity or scoped integration, action and source reference with the job. Reauthorize according to execution policy on replay. A job requeued after suspension cannot silently resume sending. Bound per-tenant backlog so a large stock import leaves other merchants able to pick. |
| Files, photos, labels and exports | Resolve object ownership in a tenant-scoped manifest. Mint a short-lived download only after authorization. Bind export creation, completion, status and retrieval to the same merchant. Give two merchants identical external IDs and verify that A’s generated export includes only A’s records and objects. |
| Caches, search and reporting | Partition keys, indexes or mandatory search filters by tenant. Include site or role scope when the response varies by permission. Check suggestions, facets, totals, pagination cursors and cached failures as well as individual hits. Purge or reindex from authoritative merchant data on a move. |
| Webhooks and integrations | Scope credentials, signing secrets, subscriptions, dedupe sets and cursors to the source installation and merchant. Route a retry to the still-authorized endpoint. Suspend delivery on offboarding and audit any authorized replay after reactivation. [Merchant API contract](../integrations/merchant-api.md) |
| Support access | Grant a named support person time-limited access to a specified merchant, site, purpose and action. Separate stock corrections from diagnosis. Record requester, approver, start, expiry, affected records and outcome in an access history available to the authorized merchant administrator. Confirm expiry with a real denial. |

## Moving a merchant between layouts

Take a consistent per-tenant snapshot at a recorded position and inventory the files it references. Preserve tenant and resource IDs, sites, users and grants, open reservations, command outcomes, unresolved observations and delivery checkpoints. Restore into the destination with outbound consumers paused. Catch up later changes, fence old writers including jobs, drain in-flight work, then reconcile the final position. Change the directory mapping only after matching balances by variant/location/disposition, open work and file hashes. Resume exactly one outbound publisher. For reversal after new writes, reconcile and transfer them back before restoring the old route.

Run the move with two fictional merchants sharing the same SKU and order number. B’s orders must continue while A moves. Compare manifests, prove that B’s files and records are absent from A’s export, replay A’s interrupted receipt and inspect each merchant’s search and webhook results. A pooled disaster backup may legitimately contain both merchants and must remain under recovery-operator control. Deliver a tenant-scoped export to a customer. [PostgreSQL dump scope](https://www.postgresql.org/docs/18/app-pgdump.html)
