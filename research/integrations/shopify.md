# Shopify as the first retail connector

**Pilot decision.** Choose Shopify if the merchant actually takes orders through it, controls the warehouse and store locations in Shopify, and can supply test transactions for checkout and counter sales. Start with merchant-managed locations and a read-only comparison against opening counts and open orders. Enable writes after staff can explain a sale, pickup, refund and transfer across both systems. This is a documentation review conducted on 26 November 2026. A merchant installation and end-to-end tests are still outstanding.

**Version.** Pin Admin GraphQL requests to `/admin/api/2026-10/graphql.json` and the webhook configuration to `2026-10`. Shopify lists this stable version as accessible until **16 October 2027 at 15:00 UTC**. Review release notes before the 2027 pilot and each quarter. Rerun the tests below on the replacement version before the deadline. Log the version returned by Shopify so an automatic fallback is visible. [API version schedule](https://shopify.dev/docs/api/usage/versioning) · [2026-10 changes](https://shopify.dev/changelog/release-notes/2026-10)

## Who tells the customer a pickup is ready?

Choose one sender for each order source and staff workflow. The Admin GraphQL pickup mutation documents an automatic customer notification. In Shopify POS Pro, a new-order push alerts store staff. Later, the clerk sets aside the goods and selects **Send notification**. For Online Store orders this sends the customer notice. For Facebook & Instagram orders in POS, the same action marks the order ready and Shopify directs staff to contact the customer themselves. Record who owns that contact. Verify each combination the merchant uses before enabling a WMS sender. [Admin GraphQL pickup mutation](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/fulfillmentOrderLineItemsPreparedForPickup) · [Shopify POS pickup workflow and channel exception](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/order-management/pickup-in-store-for-online-orders)

In the pilot, stage a labeled bag and send to a merchant-controlled test recipient. Record the order source, action taken, staff alert, resulting order state and messages that actually arrive. Repeat with an interrupted API response. Reload the fulfillment order and inspect the available history before resubmitting or sending manually. If acceptance remains uncertain, assign one clerk to resolve it. At collection the slip’s QR opens the order. Staff check the current order, pickup location, customer name, order number and bags before recording handover. [Overdue and missing pickups](../operations/order-routing.md#when-a-pickup-is-overdue-or-a-bag-is-missing) · [Delayed and cancelled notifications](../experience/manager-exceptions.md#pickup-ready-messages-that-race-with-cancellation)

## Stock at each location

Map the Shopify variant and its inventory item to the WMS SKU and unit. Pair the inventory item with a Shopify location ID to identify the inventory level. Export unmapped, duplicate and untracked items for review. Count stock by location at cutover and import outstanding commitments alongside it. Check that items are active at each selling location. [Inventory objects and states](https://shopify.dev/docs/apps/build/inventory-management-apps/manage-quantities-states)

**A three-unit order against eight units leaves five available.** Shopify commits the three units when the order is placed. The WMS mirrors that demand once against the same location and keeps eight physically on hand until dispatch. Another `available -3` API call would expose only two units for sale. Shopify manages `committed` through order and fulfillment operations. Its separately named `reserved` state can hold stock for other purposes. Match states by their business meaning. The same principle applies to a POS carry-out already reflected in Shopify stock. [Shopify inventory states and order lifecycle](https://shopify.dev/docs/apps/build/inventory-management-apps)

For WMS-originated receipts, damage, counts and transfers, decide which side posts each movement before turning on writes. For a transfer represented only in the WMS, protect approved source units from sale, keep dispatched units unavailable to both sites, and release only the quantity actually received at the destination. If the merchant already posts the same transfer in Shopify, reconcile its ID and quantities first. For authoritative corrections, `inventorySetQuantities` accepts `available` or `on_hand`. Supply an `@idempotent` key for the request and a `changeFromQuantity` field on every quantity entry. An integer checks the expected prior balance. An explicit `null` disables the check, and omitting the field returns an error. For the pilot, use the expected balance and investigate both ledgers on a `CHANGE_FROM_QUANTITY_STALE` response. A stale snapshot can omit a recent sale even if a retry succeeds. [Inventory quantity management](https://shopify.dev/docs/apps/build/inventory-management-apps/manage-quantities-states) · [Set quantities](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/inventorySetQuantities)

## Edits, outages and reconciliation

- Subscribe to order creation, edits, updates and cancellations, refunds, routing completion, fulfillment moves, fulfillment changes and inventory-level updates as permitted by the installation. Verify the raw HTTPS body using Shopify’s HMAC. Persist the delivery before acknowledging. Deduplicate by shop and `X-Shopify-Webhook-Id`. `X-Shopify-Event-Id` correlates deliveries from one merchant action. Delivery order can vary, so reload the current resource before deciding which stock or fulfillment change is still due. [Webhook topics](https://shopify.dev/docs/api/webhooks/2026-10) · [Delivery verification](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) · [Ordering and recovery](https://shopify.dev/docs/apps/build/webhooks)
- On edits and cancellations, compare current lines, assignment, remaining fulfillable quantities and prior WMS handovers. Release only open commitments. Route a cancellation received after picking to staff for physical reversal. A financial refund can arrive without a returned item. Read `restockType` and its nullable location. `NO_RESTOCK` has no stock effect or restock location. `CANCEL` applies to unfulfilled units and `RETURN` to fulfilled units. Agree that staff hold returned goods until inspection, and reconcile any stock Shopify has already restored before publishing availability. [Order edits](https://help.shopify.com/en/manual/fulfillment/managing-orders/editing-orders/considerations) · [Refund line items](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/RefundLineItem) · [Restock types](https://shopify.dev/docs/api/admin-graphql/2026-10/enums/RefundLineItemRestockType)
- Recover missed events with a scheduled, paginated order query filtered by `updated_at`, an overlapping time window and a durable checkpoint advanced after successful processing. Recheck outstanding fulfillment orders. Investigate unexpected deltas, stale POS data, inactive subscriptions and unresolved writes. Show last successful reconciliation, age of differences and affected lines to staff. Older orders outside the default 60-day window need approved `read_all_orders` access or a merchant-supplied opening list. [Orders query](https://shopify.dev/docs/api/admin-graphql/2026-10/queries/orders) · [Order access window](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/Order) · [Webhook troubleshooting](https://shopify.dev/docs/apps/build/webhooks/troubleshoot)
- Independently poll `InventoryLevel.quantities` by item and location. Changes to `committed`, `reserved`, `damaged`, `safety_stock` and `quality_control` do not themselves trigger inventory webhooks. Compare these balances even when the order cursor shows no changes. [Inventory webhook coverage](https://shopify.dev/docs/apps/build/inventory-management-apps) · [Inventory level quantities](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/InventoryLevel)

## Switch WMS while the shop still accepts order edits

In this proposed rehearsal, Shopify order 814 has two shirts packed in parcel P7 and one unpicked belt. The outgoing WMS lost the reply to its fulfillment submission for the shirts. During the switch, the merchant removes the unfulfilled belt in Shopify. An older order update arrives after the edit. Shopify permits edits to eligible unfulfilled items and documents that webhook delivery order can vary. [Shopify order-edit considerations](https://help.shopify.com/en/manual/fulfillment/managing-orders/editing-orders/considerations) · [Shopify webhook behavior](https://shopify.dev/docs/apps/build/webhooks)

| Who acts | What to do and record |
| --- | --- |
| Outgoing shift lead | Stop the old connector from publishing and fence further dispatch confirmations at the source. Record the pending submission, its original WMS operation and parcel IDs, the shop ID, Shopify order and line IDs, fulfillment-order references and location. Preserve incoming events durably through the changeover and note the last reconciled checkpoint. Keep P7 off the new packing list. |
| Incoming dispatcher | Refresh the current order, fulfillment records and assigned quantities from Shopify. Release the belt reservation once against its original line after confirming the edit. Replaying the older event must leave the belt cancelled. Compare P7’s contents and original reference against the carrier’s acceptance record and the staging shelf. An empty shelf alone leaves custody unresolved. |
| Store lead | If carrier acceptance and Shopify fulfillment both confirm the shirts, attach their references to the existing operation and close it. If the carrier accepted P7 but Shopify still shows the shirts open, keep physical dispatch recorded once and reconcile the outstanding channel confirmation before retrying. If evidence is inconclusive, assign P7 to a person with a review deadline and block repicking. If P7 is verified on the shelf, preserve its staged state and resolve any conflicting channel fulfillment before release. |

Before enabling the new publisher, replay the overlapping event window and show one order, zero belts owed and a single documented custody outcome or open exception for P7. If the switch must be reversed, stop the new publisher, hand its accepted actions and pending evidence back to the old connector, reconcile the checkpoint and then resume with one writer. ## Merchant access and proof

For a custom app installed on a store outside its owning organization, Shopify requires an IP allowlist for new installations starting 20 November 2026 at 11:59 p.m. ET. Configure the connector’s outbound network before merchant installation. Custom and merchant-created apps created on or after 1 December 2026 must use expiring offline tokens for Admin API access. Test token renewal while the merchant is signed out so reconciliation can continue between shifts. [Custom-app IP allowlists](https://shopify.dev/changelog/posts/ip-allowlists-are-now-required-for-custom-apps-installed-outside-your-organization) · [Expiring offline tokens for new custom apps](https://shopify.dev/changelog/posts/expiring-offline-access-tokens-required-for-new-custom-apps-as-of-december-1-2026)

For the merchant-authorized installation, check grants for orders, products, inventory, locations and merchant-managed fulfillment orders (`read_orders`, `read_products`, `read_inventory`, `read_locations`, `read_merchant_managed_fulfillment_orders`). Enable `write_inventory` and `write_merchant_managed_fulfillment_orders` only for the agreed writes. Confirm required staff permissions, including `fulfill_and_ship_orders`, on the installed shop. Third-party-managed fulfillment orders have different access rules. Confirm distribution type and protected-data access before depending on recipient addresses or contact details. [Access scopes](https://shopify.dev/docs/api/usage/access-scopes) · [Offline access tokens](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/offline-access-tokens) · [Protected customer data](https://shopify.dev/docs/apps/launch/protected-customer-data)

1. In a test shop, configure the pilot’s two locations, tracked variant, routing, pickup and POS fulfillment settings. Use a checkout test order and a separate authorized counter transaction on a configured POS device. Collect redacted order, line, location and fulfillment-order IDs. Observe actual quantities before and after each action.
2. Walk through eight warehouse units and two store units. Import an online order for three twice. Carry one out at the store. Confirm five available at the warehouse and one at the store. Approve a transfer of three, receive two, and explain the one still in transit. Confirm the destination becomes available only for units received.
3. Repeat with a short pick, edit, cancellation, refund with and without restock, pickup before and after collection, and a disconnected register that later syncs. Drop a webhook and replay another out of order. Interrupt a fulfillment response and confirm a single handover. Capture balances on both sides and any protected-field or permission errors.
4. Proceed to merchant writes after the read-only trial reproduces the commercial orders, location-level promises and handovers. Record differences that require the merchant’s register practice, routing configuration or scope grants to change. A successful synthetic webhook alone cannot establish those facts.
