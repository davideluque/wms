# Connecting a Venezuelan retailer’s existing business system

Ask the merchant to name the software at the register **and** the system in which the stock controller closes the day. They may be two modules of one suite, a separate checkout such as Shopify, or a register that sends transactions later. Begin with a redacted, read-only sample from the deployed system. Match a physical handover to one transaction before proposing a connector.

None of the cited materials establishes an outside WMS contract for authentication, record keys, incremental retrieval, change events or safely repeated writes. Confirm any such contract with the merchant and its authorized provider. The proposed pilot needs only a merchant-provided sample and a shadow ledger. No live account, database access, license entitlement or supported write interface was tested.

## One shadow replay for all three candidates

Use one merchant, one register, one store and one SKU. In this hypothetical case the opening count is **18 individual bags**. The invoice and delivery note refer to the same sale. The merchant confirms that the physical event is the counter handover. Preserve the source documents as evidence, including the invoice reference when the same handover appears in more than one export.

| Input received | Expected WMS result |
| --- | --- |
| Sale 501, line 1, quantity 1, package `BUL`. The file has no verified pack mapping. | Keep the line pending. The ledger remains at 18 physical bags. Flag availability as uncertain for this SKU until staff verify the handover and count, so later orders cannot rely on that stale figure. |
| Operator checks the printed pack and register line. For this supplier and date, one `BUL` contains six bags. | Save the dated mapping and reprocess the original line. Confirm **18 − 6 = 12** bags on hand. Keep the original quantity and package beside the six-unit movement. |
| The register re-exports sale 501, or its central office includes it in a later batch. | Match the original merchant, source transaction, branch, document series and stable line identity. Map local and central references where needed. One handover remains posted and stock stays at **12**. If no reliable line match exists, send the duplicate candidate to review. |
| The merchant issues a credit for two bags. A worker later receives those two back and isolates them. | Link the credit to the original sale. The credit alone changes zero physical units. After the verified return, physical stock is **14 = 12 available + 2 held**. A repeated return posts once. A later authorized release changes availability and preserves the original sale and return. |

Ask for a separate transfer example showing who posts departure and arrival. Compare a transfer document marked complete for six bags with the receiving worker’s count of five. The unresolved bag must have a named owner for investigation. If the source immediately credited six to the destination, record the reconciliation difference and suppress promises against the unsupported unit. ## Evidence needed to choose the handoff

- **Register and stock controller.** Obtain product, version, edition and modules, merchant and branch codes, register or document series, warehouse or *depósito* codes and their effective mappings. Request one variant or package label, the corresponding dated catalog record and a stock report broken down by warehouse.
- **Dispatcher and accounting.** Trace one anonymized order through delivery note, invoice, void or credit and actual handover or return. Preserve document and line references, pack, unit, timestamps, original and changed states, and both sites on a transfer. Ask whether the same order can split across dispatches and which record staff trust when paper and screen disagree.
- **Vendor or authorized local partner.** Request the supported extraction procedure, an example file and field definitions, access rights, and a second overlapping extract after a correction. For a proposed automated integration, also obtain versioned interface documentation, identity rules, catch-up behavior, retry policy and a supported test environment. Record limits and human reconciliation steps where only reports are available.

Select the first connector by the retailer’s actual install and the repeatability of this replay. If Shopify originates the order and a local system invoices it, agree which system authoritatively reports physical handover. If a local register captures the same counter sale before central sync, agree how both copies resolve to one event.
